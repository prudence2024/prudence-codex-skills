01.  Quick overview of AI coding tools 8 min
“Imagine Lego got bitten by a radioactive AI…” — that’s pretty much any LLM for coding in a 
nutshell. It's everything you need to build something amazing, but comes with AI. Y ou 
orchestrate the construction but everytime you get stuck, you can just say, "fix this."   Cursor 
keeps the familiar look-and-feel of a desktop code editor, but tucks an LLM right next to your 
files so you can ask, edit and run without ever leaving the window. Let’s walk through the bits 
you’ll use on day one.
Opening the hood
When you launch Cursor for the first time you’ll land on something that looks suspiciously like VS 
Code because it is VS Code under the hood, just with extra AI plumbing.  If you don't know what VS 
Code it, that doesn't matter either frankly!  It's just a code editor that's very popular and what has 
helped Cursor become so popular among developers as it's like working in the same environment 
they're already used to. 
Here is where you choose what LLM you want to use.  Cursor now tells you if advanced models will 
costs you per question you ask it.  Hint:  Stick to the free ones unless you've got money to burn!
The application is split into 3 distinct sections:
1. File Explorer (far left).This is the IKEA shelving of your project: folders, files and a little '• button to 
add new ones.  
2. Editor Pane (centre stage).The big canvas where your code (or soon-to-be code) lives. Standard 
line numbers on the left, tabs across the top.
3. Chat/Diff Pane (right-hand column).Here’s the secret sauce: a rolling conversation with the AI 
plus an inline diff viewer. Ask a question, preview the suggested change, then thumbs-up or 
thumbs-down it. 
4. A Mini Console Window (below).
Here you can run your own little terminal window (or multiple ones), look at active problems 
detected in files, run you client (front end) and server (back end) locally for development, and 
see the logs that appear if you code them in.
5. Status Bar (very bottom).A neat little badge shows which model is active (e.g., GPT -5.2). Click it 
to swap brains later on.
What about Claude Code, or others?
If you're running these within VS Code or Cursor, then they can run from a terminal window.  Some 
people (like me) prefer that and it's still connected to Cursor or VS Code.  However, now, these 
platforms are almost all accessible via web browser, or as a stand alone app.  I would always suggest 
a stand alone app model as you're in more control of the environment and the data.  Y ou're not 
always relying on an internet connection just to power the UI.  At least you can browse your code 
locally and get to files.  Web-based code builders limit that and you need to log in before you can see 
anything.

Best-practice quick hits
• Start Small: On day one, point your AI at a tiny project (even a single .py or .ts file). It’s like 
learning to drive in an empty parking lot.  
• Talk in Goals, Not Steps: Instead of “type print,” say “Show a greeting on-screen.” The AI fills the 
gaps.  
• One Change at a Time: Accept or discard after every preview. Long chains of unaccepted 
orange boxes can get messy fast.  
• Narrate Y our Rejections: If you scrap a suggestion, tell the model why (“Too verbose” or “Wrong 
function name”). Future answers improve. 
• Screenshot Troubles: When something looks weird, grab a screenshot and paste it into chat. AI 
can read images and debug UI glitches.

Why a dev !’ test !’ prod pipeline matters
If you're going to do this properly when you build your first real app, then you need to have some way 
to build and test without breaking a working version of your app.  This is even more important if you 
have deployed an app and it has users on it.  The last thing you need to be doing is live changes to 
things that are in production without testing them first.
1. Dev = your computer. Messy, experimental, private.  
2. Test / staging = a shared server where you click around and break things safely.  This will be 
hosted somewhere which is more like a clone of your production environment so should be very 
similar.  It's like pre-production. Websites like Vercel and Railway will give you a hobby account 
for free so you can set this up. (Links to these platforms are in the Resources section.
3. Prod = the live site that customers touch, where you may generate revenue, grab customer 
data.   This one you don't mess with.

Meet localhost
When you have your client installed (eg. Vite), you can then open Chrome or Safari and browse to 
http://localhost, you’re talking to your own machine. It’s lightning-fast and free, but remember it’s not 1-
to-1 with production.  Notice there's no "s" in "http://" as you don't have a security certificate.  
Everything is running on one machine, inside the same network.  This is not realistic of production at 
all but it's great to build something locally and test it to make sure the vast majority of the functionality 
works.  Y ou can still connect it to other sites for things like authentication, databases, and calling 
other APIs.   
Things that can differ to production:
• Permissions – you have admin rights locally; your cloud host probably won’t.  
• Networking – company VPNs, firewalls, or HTTPS certificates add layers you don’t see at home. 
• Security – browsers may block cross-site cookies when online or only in “real” HTTPS 
environments.
Treat localhost like a rehearsal studio: perfection isn’t required, but practice saves on-stage 
embarrassment.
If you want to run more than one app locally, can you do that too!  Y ou would simply change the 
port number (or have the AI do it for you).  This means the default port when you go to http://
localhost is port 80, but you can have your webserver for each app have a different port 
number.  Like 1000, 1001, 1002... so when you go to http://localhost:1000 you will see 
something different to the default port (80).  Y ou will just be creating a new web server each time 
in different folders and can run them independantly. 
For axample, if you have AI build you a Vite web server, it has a configuration file where it will set the 
port for you and tell you how to access it.  If your dev machine has wifi and a connected ethernet 
cable, you can even run Vite in a way that allows others in your home network to see the site from 
another laptop or phone.  Great for having another user in the family test.  (hint:  you would start the 
web server with the command npm run dev -- --host).
When you’ll need Docker Desktop
For these front-end demos Node’s simple server is plenty. The minute you add:
• A database (Postgres, Mongo)  
• A back-end API (Flask, Express)  
• OS-specific dependencies (ImageMagick, ffmpeg)

03.  Understanding AI coding rules and configuration 8 min
Rules: Your “House   Style” File
AI is the chef; and a rules file is the recipe card you slip under the kitchen door.
When AI knows your tastes (tech   stack, naming quirks, lint rules), its suggestions stop feeling 
“generic GitHub” and start sounding like your codebase.
Start with a chat about your stack
Before you write a single rule, spend five minutes talking to AI (Cursor or ChatGPT / Claude) about 
the tech choices for this project. That clarifies what the rules should lock in.
Sample discovery prompts
We’re building a SaaS dashboard. But I really have no idea where to begin.  I need 
something...
I’m a just starting out and ready to build my first web app.  It's going to be a 
moitivator ...
Use the answers to decide:
• Languages (TypeScript vs JS, Python vs Go)
• Framework flavours (Next.js vs Vite, Flask vs FastAPI)
• Testing / linting tools (Playwright, ESLint, Ruff)
Everything you nail down here becomes a rule that keeps AI from drifting later.
Where rules live
Cursor processes rules from two places every time it generates code:
1. Global settings – open Settings !’ Rules in the top   right gear icon. Rules here apply to every 
project you open.
(insert screenshot of Cursor settings panel highlighting the Rules tab)
2. Project file – a plaintext file named .cursorrules sitting at the root of the repo. These override or 
add to the global ones only when that folder is active.
Why both? Global rules handle personal habits (“Always write comments like I’m five”). Project   level 
rules handle stack   specific demands (“Use Tailwind utility classes, avoid inline styles”).
Claude Code has its own markdown file (it's called claude.md), and so does Codex.  Sometimes for 
the web-based apps these are found in the system settings.  If you don't know, just ask the tool you're 
using about how to setup the rules file properly!  Then, ask it to write the rules for you.  Every few 

--- PDF PAGE 8 ---
weeks, do a sanity check.  Maybe your project has changed or added a new techie bit, so the rules 
should be updated to reflect that.
Best   practice cheat   sheet
• Be prescriptive, not verbose. Ten crisp rules beat fifty vague paragraphs.
• Lead with do, end with don’t. Positive commands first, prohibitions second.
• Version your rules. Add a header: # v1.2 – 2025   05   01 – switched to Go 1.22.
• Keep secrets out. Rules live in the repo; don’t paste API keys.
• Iterate. If AI drifts, update the rule instead of nagging in every prompt.
• Stay in sync with tooling. When Prettier or Black upgrades, update the rule so AI matches the 
formatter.
• Reference docs, not blogs. e.g. “Follow React docs for useEffect cleanup.” Links age; official 
docs update.
• Reuse. Save proven rule   sets in a personal “rules vault” and copy them into new projects.

04.  Key files you need in any project 11 min
Keeping /Y our /Project /Well Documented: README, CHANGELOG, BUGS & ENHANCEMENTS in plain 
English
Think of these three Markdown files as your project’s memory palace.  They tell you, /future   you, and AI 
what the code does, why it changed, what's not working right, and what you’d like to build next. The 
clearer that story, the smarter (and less repetitive) the AI’s answers become.
Key thing to remember here is that you will not be writing these documents, the AI will!  
Y ou just need to remember to tell it to update these files and also tell it what you want in them!
So what's the point?  Simple, it's all about context.  Every time you start a new chat, load up these 
files into the chat window.   Just highlight all the text and press "Add to chat" or copy, go to the chat 
window and paste.  It will attach the file without all the text.  Then, when you start your new chat 
session, the AI is instantly up to speed on what your app does and is ready to dig in to look at code, 
find things, and understand the big picture so it doesn't ask you silly questions!
Y ou will be creating hundreds of chat sessions for a compex app because the context window isn't 
big enough to hold all the information you discus without purging some of the data.
README.MD
A good README is helpful to the AI with this information.
1. What does this project do? - overview, website, problem statment, how it works.  
2. What is the tech stack - useful to have have the tech stack and configuration.
3. Key features - a list of the main ffeatures of the app
4. Share a tree view of the files and descriptions - add a one-line description to each file so you 
know what they do
5. How would you install this from scratch? - installation instructions, dependencies, external 3rd 
party integration parameters, environment variables
6. How would you deploy the project - where is it deployed and what was needed to do that?

05.  Chat optimisation hacks 10 min
What /is /a context window, anyway?
Every language model has a “short   term memory” bucket called a context window. Picture a rolling 
scroll of the last N tokens (roughly words + punctuation) the model can see. When the bucket 
overflows, the oldest stuff falls out—or gets summarised. Bigger windows (Claude /Sonnet’s Ø=Ü¾ /200   k 
tokens) hold entire PRDs; smaller ones forget after a few pages. /
How size impacts speed & quality
Size Feels like Trade   off
Small ("d /32 /k) Snappy responses, cheap Needs surgical prompts; loses 
long conversations quickly
Medium (64–128 /k) Good balance for most coding Slightly higher latency, higher cost
Huge ("e /200 /k, Claude/Gemini/
Codex)
Swallows your 100   page PRD 
whole
Slower first token, pricey, may

I use a M4 Mac /mini with 16 /GB RAM as my dev machine but that isn’t the bottleneck, these limits live 
on the cloud model’s side. So if replies get vague or AI suggests a “start new chat” banner, it’s usually 
wanting to prevent the context hitting the ceiling, not your hardware.
Finding your rhythm: one chat per revision
Revision /= code you actually shipped (accepted & maybe committed).
That’s a natural breakpoint to spin up a fresh chat because:
1. The codebase just changed so new files and functions deserve a clean context.
2. Y ou’ll paste the updated README, CHANGELOG, and and what you want from this next stage.
Pro tip: When Cursor nags you mid   brainstorm (“Start a new chat?”) but you haven’t accepted 
any changes yet ignore it. Finish the idea first, then move.
Context windows now are much larger.  200k to 1 million tokens, but there's still something called 
"Context Rot" where things get worse over time.  Claude Code runs a "compacting conversation" 
process and after each one, things may get worse.  So, it's still good practice to update your docs, 
and then start a new session regardless to keep that context clean. 
Best   practice cheat sheet
• One chat per revision. New feature? New chat.
• Seed new chats with README, latest CHANGELOG entry, and final two messages from the old 
chat.

06.  Build out your Products Requirement Doc (PRD) 13 min
Why write a PRD?
A PRD seperates the boys from the men.  If you want to build a genuine piece of enterprise-grade, 
revenue-generating software, you're going to want to take this job seriously and you're going to need 
a plan.  The PRD is your plan to do this right, and sets the foundation.  Sure, that simple calcuator 
app didn't need anything like this, but if you're going to build that next SaaS app that generations a 
few thousand pounds a month for you, there needs to be structure.  
A well   written PRD is the single cheapest insurance policy you can buy for a software project. /Without 
one, every project becomes a a car crash: requirements mutate as they bounce from idea to idea 
("oh and we should have that too!") and the finished product often solves a different problem than the 
one that inspired it. / A PRD freezes the conversation in time. /It spells out the pain point, the audience, 
the success metrics, and the things you /won’t /do. / Because those decisions are captured in plain 
English rather than buried in Slack threads or half   remembered calls, new teammates (or future   you) 
can absorb months of context in minutes instead of days.
That clarity pays technical dividends too. AI reads the PRD just like a human. /When the 
document says “Front end is React 18, back end is FastAPI, billing runs through Stripe Pro 
plan,” the model stops guessing and starts generating code that actually fits your stack and 
roadmap. /Y ou reduce hallucinated features, trim back   and   forth prompt cycles, and avoid costly 
rewrites down the line. / In short, a PRD turns abstract vision into a concrete contract between 
product, engineering, and AI—keeping everyone rowing in the same direction from first commit 
to final deploy.
Pain without a PRD Pay   off with a PRD
Endless “scope   creep” debates Clear in   scope vs out   of   scope bullets
Five teammates read one Jira ticket five different ways One doc everyone (and Cursor) can quote
Success criteria invented during the demo Metrics baked in from day /1
New hire asks “What does this repo even do?” README shows how to run; PRD shows why it exists
"scope-creep" - when new things get added all the time as they might sound small at the 
beginning but just get piled on.

 /8.4 /Where does the MVP live?  
Defining the Minimum /Viable /Product is like drawing a finish line everyone can see. This section 
explains why the [MVP] tag belongs inside the PRD (rather than a separate doc), how it keeps 
feature creep at bay, and how AI prompts can filter for those tags to stay laser   focused on what must 
ship first.
MVP = Minimum /Viable /Product — the thinnest slice that proves the idea.  Many build an MVP for 
testing, seeing if people will pay a little to use it, promote it to investors, etc.  It's a great first step.  "Is 
this a real thing or not?". 
Mark it inside Section /5.1 with [MVP] tags or a dedicated bullet list. Keeping the flag in the PRD:
• Guarantees AI sees what must ship first.  
• Lets prompts say “Implement [MVP] items only.”  
• Shows stakeholders how Phase /2 features fit the roadmap.
