More Complex Apps Require More Planning and Looking Ahead
The real secret to building production-ready apps isn't just writing great code but it's setting yourself 
up with a strong development process. Before you even start building, it helps to think through where 
your code will live, how you’ll test it, and how you’ll know it’s safe to release.
For a small business or a solo builder using AI tools like Cursor/Claude Code, this can feel like 
overkill but it’s not. It’s how you protect yourself from late-night emergencies, broken features, and 
costly bugs in production.
Why This Matters (Especially for Small Teams)
Let’s say you’re building a membership site for a fitness coach. Y ou start out just testing it on your 
laptop: logins work, videos play, payments seem fine. So you go ahead and push it live.
A few weeks later:
• Y our real users start getting auth errors. (Due to a single SQL query you ran)
• Payments are being duplicated, or are they? Y ou can't tell. (Thanks to an update in your 
webhook from Stripe)
• The workout video player stops working on mobile. (Y ou did a security assessment and made 
your content security policy far too strict)
• Y ou realize some things only broke after you made “quick fixes” late one night. (And wake up to 
emails and a host of pain to start your day!)
Now, you’re scrambling to fix it while customers are emailing in. That’s stress you didn’t need  and it 
all comes down to having no separation between development, staging, and production.  Y ou should 
be focusing on building!  Not getting sidetracked wasting precious hours trying to squash more bugs 
you didn't anticipate you woul dget.
If you had planned out those environments ahead of time, you’d have caught most of those issues in 
a safer space first.

How Planning Ahead Saves You (A Lot)
Without this setup, you’ll find yourself:
• Copy/pasting changes into prod and hoping nothing breaks
• Making changes in staging and forgetting to sync them to dev
• Getting surprised by bugs that only show up online
• Having to halt development while you fix broken prod builds
When you’ve planned ahead:
• Y ou avoid "Oh no!" moments after hitting deploy
• Y ou save money by only paying for hosting once your app is stable
• Y ou can move faster, because you’re not constantly worried about breaking things
• Y ou can build trust  with clients, users, and even yourself

architecture considerably.

Testing with Preview Deployments in a Staging Environment
Once you’ve planned your environments and set up your GitHub branches (like dev, staging, and 
main), the next big step is preview deployments. This is how you test your app in a real, hosted 
environment before sending it to production, just to make sure all is working just as expected before 
pushing to production. 
Tools like Vercel and Railway make this incredibly easy: every time you push changes to a certain 
branch (like staging), they automatically build your app and give you a live link to test it.
What Is a Preview Deployment?
A preview deployment is a full, online version of your app tied to a specific branch in your GitHub 
repo that you can visit, click around, and test like a real user.
For example:
• Y ou push code to your staging branch
• Vercel detects the change
• It builds your frontend and gives you a live URL like:
https://your-app-staging.vercel.app
• Y ou click the link, and bam — your new feature is running live, but only in staging
This is game-changing because it lets you:
• Share your work with teammates or clients before releasing
• Catch layout issues, mobile bugs, or loading problems early
• Safely test auth flows, form submissions, and logic
• Debug in a real environment (not just locally)

Additional Considerations for a Complex Environment
So far, we’ve talked about Dev !’ Staging !’ Production setups, preview deployments, and testing 
workflows. But how do you know when it’s time to take things further? When does your app need 
more than just Vercel and Supabase? What happens when you hit limitations or need more control?
Let’s explore when and why you'd start layering in more infrastructure and the real-world tradeoffs to 
consider.
When Do You Need a More Complex Setup?
Not every app needs to spin up its own servers or run custom backends. But the moment your app 
starts moving beyond static pages and into user logic, data processing, or tight performance 
requirements mean it’s time to evaluate.
Here are common signals that you might need more:
'   You’re building a single-page application (SPA)
Modern SPAs often use frameworks like React or Svelte, and they rely heavily on APIs and dynamic 
routing. Y ou’ll need to think about:
• Caching and revalidation
• Real-time updates
• Browser vs. server rendering
• How your auth logic works in a client-rendered app
Vercel is great for SPAs, but once you start needing custom backend logic, that may need to move 
elsewhere.

--- PDF PAGE 10 ---
'   You’re storing and manipulating user data
Even if you're using Supabase, once you're dealing with user data (profiles, uploads, custom 
dashboards), you're now responsible for data consistency, security, and performance.  Not to mention 
adhering to GDPR rules!
Y ou’ll start asking:
• How do I seed different databases for staging vs. prod?
• What sort of security do I need? (Go back to the Security Module!)
• Where do I go to access the logs across all these environments?
'   You have authentication and permissions
Anything with user logins, roles (admin, editor, viewer), or gated content raises the complexity quickly.
• Supabase helps here, but integrating auth in a real-world app still means wiring it into the UI, 
backend, and database correctly.  Thankfully Cursor can help with all that!  However, you will 
need to consider what is behind a user login and what isn't.  How to protect the authenticated 
content.  How to stop one user from accidentally accessing another users' informiaton, etc. 
• Y ou might want to mock certain users for testing, or simulate login flows in staging.  Also, if you 
use tiers for different levels of access for features, build a way to move users between tiers so 
that you can test feature access at all levels.
When Do You Outgrow Serverless Platforms Like Vercel?
Vercel is fantastic for static and dynamic frontends. But it’s not a full backend, and serverless does 
come with tradeoffs especially if you’re running anything more than light API calls.
What is Serverless Architecture?
Serverless architecture is a way of building apps where you don’t manage servers yourself. Instead, 
you use services (like Vercel, AWS Lambda, or Supabase) that run your code or store your data on 
demand — and only when needed.
Y ou still need servers behind the scenes, but you don't set them up, maintain them, or keep them 
running 24/7. The platform handles that automatically.
Key traits of serverless:
• Y our code runs in small functions (like an API endpoint)
• These functions spin up automatically when triggered
• Y ou only pay when they’re used
• Great for things like: simple APIs, user authentication, form submissions, static sites

--- PDF PAGE 11 ---
Y ou build a contact form !’ when someone submits it, a serverless function handles the request, sends 
an email, then shuts down. Y ou never deal with the server at all.  It’s fast, scalable, and great for 
smaller apps — but has limitations for long-running tasks or complex backend logic.
Here are some limits to be aware of:
& þ   Cold Starts and Execution Limits
• Vercel’s serverless functions have execution timeouts (typically 10 seconds)
• Y ou may hit issues with cold starts (a delay before the server spins up)
• Long-running tasks like generating PDFs, uploading videos, API calls to a 3rd party service (like 
ChatGPT), or complex database queries may fail silently or time out
& þ   Limited Background Jobs
Need to send an email 2 minutes after signup? Or queue up a batch process? That’s not really what 
Vercel was built for. Y ou’ll need:
• Something like Brevo to hold a contact list that can automatically send out emails when a new 
user is added to the list 
• Or a traditional backend with cron jobs (which is where platforms like Railway, Render, or Fly.io 
come in)
Why You Might Add a Platform Like Railway
Railway, Render, or even self-hosted Docker setups start to make sense when:
• Y ou need longer running processes (eg. Make a call to ChatGPT's API to get answers to some 
data that you're analysing for a user)
• Y ou want to run your own custom backend APIs (Express, FastAPI, etc.)
• Y ou need full control over logs, environments, and background workers
• Y ou’re working with non-JavaScript tools, like Python, Go, or Rust backends
They’re often used alongside Vercel where the frontend on Vercel, backend on Railway.
Example:
• Frontend: Vercel (React)
• Backend API: Railway (Node.js/Express)
• Database: Supabase
• Auth: Supabase
• Staging: duplicated Railway project and Supabase instance with separate keys

Database Considerations
Once you’re storing any real data, you’ll need a proper database and that comes with its own list of 
decisions.
Key things to think about:
• Separate staging and prod databases to avoid overwriting real data
• Do you want to host your own database or use managed services like Supabase or 
PlanetScale?
• How do you handle schema changes across environments?
• Do you need replication, backups, or regional availability?
Tools like Supabase are incredibly helpful but remember:
• Even their lowest plan (~$10 SGD/month) only covers one project
• If you want staging + production, you’re doubling that cost
• Y ou may also pay extra for bandwidth, storage, and auth limits so keep an eye on your usage.
