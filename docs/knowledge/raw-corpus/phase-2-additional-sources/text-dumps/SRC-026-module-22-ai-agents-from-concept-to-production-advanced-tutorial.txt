01.  Understanding AI agents and agentic workflows 22 min
Understanding AI Agents and Agentic Workflows
In Module 20, we introduced AI agents as the personal chef who grocery shops, cooks, and plates 
the meal while you simply say "something Italian tonight." Y ou learned the basic agentic loop - 
perceive, plan, act, observe, repeat -- and compared the major platforms.
Now it is time to open the hood and understand how that chef actually thinks. Because once you 
move from using agents to building them, the difference between a clumsy bot and a genuinely useful 
assistant comes down to the workflow patterns, memory systems, and reasoning strategies running 
under the surface.
Think of it this way: Module 20 taught you to drive the car. This module teaches you how the engine 
works so you can build your own.
From Simple Chains to Agentic Workflows
Before we go deeper, let's clarify an important distinction that trips people up.
A chain is a fixed sequence of steps. Input goes in, passes through Step A, then Step B, then Step C, 
and output comes out. Every run follows the exact same path. Most "AI automation" you see on 
Y ouTube is actually a chain - it looks impressive, but it cannot adapt when something unexpected 
happens.
An agentic workflow is a dynamic sequence. The agent decides which step comes next based on 
what it observes. It can loop back, skip ahead, call for help, or abandon a path that is not working. 
The route is not pre-programmed; it emerges from the agent's reasoning.
Here is a concrete example:

The Agentic Loop in Detail: Observe, Think, Act, Reflect
In Module 20 we introduced the loop as "Perceive, Plan, Act, Observe, Repeat." Let's refine that into 
the four-phase model that most agent frameworks actually implement:

--- PDF PAGE 3 ---
+---> OBSERVE ----> THINK ----> ACT ----> REFLECT ---+
|                                                      |
+------------------  LOOP BACK  <---------------------+
1. Observe -- The agent gathers information. This could mean reading files, querying a database, 
calling an API, parsing a web page, or simply re-reading the user's original request. Observation is 
the agent's sensory input.
2. Think -- The agent reasons about what it observed. This is where the LLM shines as it evaluates 
the situation, considers options, and decides what to do next. In framework terms, this is often called 
the "planning" or "reasoning" step.
3. Act -- The agent executes a concrete action. It might write a file, call a tool, send a message, or 
generate a response. Actions change the state of the world.
4. Reflect -- The agent evaluates the result of its action. Did it work? Did it move closer to the goal? 
Should it try something different? Reflection is what separates a genuine agent from a script that 
blindly runs steps in order.
The key insight is the loop. After reflecting, the agent goes back to observe the new state of the world 
and decides what to do next. This continues until the agent determines the goal has been met (or it 
gives up after too many attempts).
Why this matters for you: When you build an agent, you are designing each phase of this loop. 
What can the agent observe? What tools can it use to act? How does it decide when to stop? 
These are the engineering decisions that determine whether your agent is useful or frustrating.
The ReAct Pattern: How Modern Agents Reason
If you read any AI agent documentation, you will encounter the term ReAct within the first few pages. 
It stands for Reasoning + Acting, and it is the dominant pattern for how LLM-based agents work today.
The idea is elegantly simple: instead of having the agent just take actions, you force it to write out its 
reasoning before each action. This makes the agent more reliable because the reasoning step helps 
it think through the problem before jumping to a solution.
Here is what a ReAct loop looks like in practice:

--- PDF PAGE 4 ---
User: Find the total revenue from last quarter and email it to Sarah.
Agent Thought: I need to find last quarter's revenue. I should check
the database for sales records from Q3. Let me query the sales table.
Agent Action: query_database("SELECT SUM(amount) FROM sales
WHERE quarter = 'Q3_2025'")
Agent Observation: Result: $247,500
Agent Thought: I have the revenue figure: $247,500. Now I need to
email this to Sarah. Let me compose a professional email with
this information.
Agent Action: send_email(to="sarah@company.com",
subject="Q3 Revenue Summary",
body="Hi Sarah, the total revenue for Q3 2025 was $247,500.")
Agent Observation: Email sent successfully.
Agent Thought: Both tasks are complete. The revenue was retrieved
and the email was sent to Sarah. I can provide a final summary.
Agent Response: Done! Q3 revenue was $247,500 and I've emailed
the summary to Sarah.
Notice the pattern: Thought -> Action -> Observation, repeated until the task is complete. The 
"Thought" step is the magic ingredient -- it gives the LLM a scratchpad to reason before committing 
to an action.
Why ReAct works so well:
• Forces the agent to plan before acting (fewer mistakes)
• Creates a visible chain of reasoning (easier to debug)
• Allows the agent to course-correct mid-task
• Produces a natural audit trail of what happened and why
Every major agent framework -- LangChain, CrewAI, Claude's agent capabilities, OpenAI's Agents 
SDK -- implements some variation of ReAct under the hood.

Agent Memory: Short-Term vs Long-Term
Human brains have working memory (what you are thinking about right now) and long-term memory 
(things you learned years ago). Agents need both too, and understanding memory is critical for 
building agents that do not forget what they were doing halfway through a task.
Short-Term Memory (Context Window)
This is the conversation history where everything the agent has seen and done during the current 
session. It is stored in the LLM's context window, which has a fixed size limit.
The problem: Context windows are large but not infinite. Claude's context window is (as of this 
writing) 200K tokens (roughly 150,000 words). GPT -5 is about the same. That sounds like a lot, but 
when your agent is reading files, receiving tool outputs, and accumulating reasoning steps, it fills up 
fast.
What happens when memory fills up: The agent starts "forgetting" earlier parts of the conversation. It 
might re-read a file it already read, contradict an earlier decision, or lose track of the original goal. 
This is one of the most common failure modes in agent systems.
Strategies for managing short-term memory:
• Summarise earlier steps periodically (condense 5 pages of reasoning into a paragraph)
• Only keep the most relevant tool outputs (discard raw data after extracting key facts)
• Break large tasks into subtasks that each fit comfortably in context

--- PDF PAGE 6 ---
Long-Term Memory (Persistent Storage)
This is information that persists between sessions. It is stored outside the LLM in a database, vector 
store, or file system.
Examples of long-term memory:
• User preferences ("Sarah prefers bullet-point summaries")
• Project context ("This codebase uses React with TypeScript and Tailwind")
• Past interactions ("Last week we decided to use Supabase instead of Firebase")
• Knowledge base (documentation, FAQs, company policies)
How it works in practice: Before the agent starts reasoning, a retrieval step searches long-term 
memory for relevant context and injects it into the prompt. This is often called RAG (Retrieval-
Augmented Generation) -- the agent retrieves relevant memories before generating its response.

Multi-Agent Systems: When One Agent Is Not Enough
Sometimes a single agent trying to do everything is like one person trying to be the architect, 
plumber, electrician, and interior designer on a house renovation. It is possible, but the results will not 
be great.
Multi-agent systems use multiple specialised agents that collaborate to complete a task. Each agent 
has its own role, tools, and expertise.
Here is a simple example -- imagine you ask a system to "build a landing page for my new product":
Orchestrator Agent: Receives the request, breaks it down into subtasks.
  |
  +-- Designer Agent: Creates the layout and visual structure.
  |     Tools: design templates, colour palette generator
  |
  +-- Copywriter Agent: Writes the headlines, body text, and CTAs.
  |     Tools: brand guidelines, product documentation
  |
  +-- Developer Agent: Turns the design and copy into actual code.
  |     Tools: file system, terminal, code execution
  |
  +-- QA Agent: Reviews the final page for issues.
        Tools: browser, accessibility checker, link validator

--- PDF PAGE 7 ---
Each agent focuses on what it does best. The orchestrator coordinates the workflow, passes outputs 
from one agent to the next, and handles any conflicts or issues.
Why multi-agent systems matter for you:
• They can tackle problems too complex for a single agent
• Each agent can use a different model (cheap model for simple tasks, powerful model for 
complex reasoning)
• They mirror how real teams work, making them intuitive to design
• They provide natural checkpoints where humans can review intermediate results
We will go much deeper into multi-agent architecture patterns in the next section. For now, just know 
that when you hear "multi-agent," think "team of specialists" rather than "one genius doing 
everything."
Agent Planning and Reasoning
The difference between a good agent and a bad agent often comes down to how well it plans.
A naive agent charges at the first subtask it identifies. A sophisticated agent steps back, considers 
the full scope of the problem, and creates a plan before taking any action.
Here are the main planning strategies agents use:
1. Upfront Planning -- The agent creates a complete plan before taking any action. Good for well-
defined tasks where the steps are predictable.
User: Migrate the database from SQLite to PostgreSQL.
Agent Plan:
1. Audit current SQLite schema (tables, columns, constraints)
2. Generate equivalent PostgreSQL schema
3. Write data migration script
4. Update application connection strings
5. Run migration on test database
6. Verify data integrity
7. Update environment variables for production
2. Iterative Planning -- The agent plans one or two steps ahead, executes them, and then re-plans 
based on what it learned. Good for tasks with uncertainty or when the full scope is not clear at the 
start.
3. Hierarchical Planning -- The agent creates high-level goals, then decomposes each goal into 
subtasks, then decomposes those further. Good for complex, multi-day projects.

--- PDF PAGE 8 ---
High-level: Build an e-commerce checkout system
  -> Sub-goal: Shopping cart functionality
    -> Task: Create cart data model
    -> Task: Build add-to-cart API endpoint
    -> Task: Build cart UI component
  -> Sub-goal: Payment processing
    -> Task: Integrate Stripe SDK
    -> Task: Build checkout form
    -> Task: Handle webhook events
The planning strategy you choose (or that your agent framework chooses) has a huge impact on 
reliability. We will cover how to implement these patterns in Section 2.
How This All Connects: An End-to-End Example
Let's put everything together with a realistic scenario. Imagine you have built a project management 
app, and you want an AI agent to handle customer support tickets:
1. Ticket arrives: "I can't export my project data to CSV."
2. Observe: Agent reads the ticket, checks user's account details, retrieves the export feature 
documentation from long-term memory.
3. Think (ReAct): "This could be a bug or a permissions issue. Let me check the user's subscription 
tier first, since CSV export might be a premium feature."
4. Act (Tool Use): Agent queries the database for the user's subscription tier.
5. Observe: User is on the free tier. CSV export requires the Pro tier.
6. Reflect: "This is not a bug,  it is a feature limitation. I should explain this politely and offer an 
upgrade path."
7. Act: Agent composes a response explaining the limitation and includes a link to upgrade.
8. Reflect: "Response sent. The ticket can be marked as resolved."
Notice how every concept we covered from the agentic loop, ReAct reasoning, tool use, and memory 
shows up naturally in this single interaction. That is what makes these concepts so important: they 
are not academic abstractions. They are the building blocks of every agent you will build.

Key Takeaways
• Agentic workflows are dynamic, not fixed -- the agent decides what to do next based on what it 
observes, unlike chains that follow a pre-set sequence every time.
• The agentic loop (Observe, Think, Act, Reflect) is the core engine of every AI agent. 
Understanding this loop is essential for building agents that actually work.
• ReAct (Reasoning + Acting) forces the agent to think before it acts, making it more reliable and 
easier to debug. Every major framework uses some version of this pattern.
• Tools are what separate an agent from a chatbot. Without tools, an LLM can only generate text. 
With tools, it can read files, query databases, send emails, and interact with the real world.
• Memory management is critical. Short-term memory (context window) fills up fast; long-term 
memory (databases, vector stores) lets agents remember across sessions. Design both 
carefully.
• Multi-agent systems let you break complex problems into specialised roles, just like a real team. 
One orchestrator coordinates multiple specialist agents.
• Planning strategy matters. Upfront planning works for predictable tasks; iterative planning works 
for uncertain ones; hierarchical planning works for complex projects. Choose wisely.
• All of these concepts work together in every real agent interaction. The loop, the reasoning, the 
tools, the memory, they are not separate features but interconnected parts of one system.

02.  Designing agent architectures 24 min
Designing Agent Architectures
Imagine you are planning a wedding. Y ou could try to do everything yourself: book the venue, arrange 
the flowers, hire the DJ, design the invitations, coordinate the catering, manage the guest list. Some 
people do this, and some of those weddings turn out beautifully. But most people who try the solo 
approach end up stressed, overwhelmed, and serving slightly cold chicken.
The alternative? Hire a wedding planner who coordinates a team of specialists. The florist handles 
flowers. The caterer handles food. The DJ handles music. The planner makes sure everyone shows 
up at the right time and nothing falls through the cracks.
Designing an agent architecture is exactly the same decision. Y ou need to figure out: should one 
agent do everything, or should you build a team? And if you build a team, how should they 
communicate, who is in charge, and what happens when something goes wrong?
This section gives you the blueprints.
Why Architecture Matters
Before we look at specific patterns, let's understand why you cannot just throw an LLM at a problem 
and hope for the best.
Without good architecture, agents:
• Lose track of what they are doing on complex tasks
• Use the wrong tool at the wrong time
• Get stuck in infinite loops (trying the same failed approach repeatedly)
• Cost you money by making unnecessary API calls
• Produce inconsistent results that you cannot trust
With good architecture, agents:
• Break complex problems into manageable pieces
• Recover gracefully from errors
• Stay within budget by using the right model for each subtask
• Produce reliable, repeatable results
• Can be debugged and improved over time
Think of architecture as the difference between a pile of LEGO bricks and an actual LEGO house. 
Same pieces, vastly different outcomes.

Pattern 1: Single Agent (The Solo Performer)
This is the simplest architecture and the one you should start with.
How it works: One agent receives a task, reasons about it, uses tools to complete it, and returns the 
result. There is no delegation, no coordination, no handoffs. Just one LLM in a loop.

When to use it:
• The task is well-defined and can be completed in under ~20 steps
• Y ou do not need different expertise for different parts of the task
• Y ou want simplicity and fast iteration
• Y ou are building your first agent (always start here)
When it breaks down:
• Tasks that require switching between very different skill sets (writing code AND writing 
marketing copy)
• Tasks that are so long the agent runs out of context window
• Tasks that need parallel execution (doing multiple things at the same time)
Real-world example: A customer support agent that reads a ticket, checks the knowledge base, and 
writes a response. One agent, one skill set, one workflow.

When to use it:
• Very large, complex projects with multiple phases
• Tasks that naturally have a hierarchy (strategy -> tactics -> execution)
• When you need different levels of oversight at different stages
• Enterprise applications where accountability and audit trails matter
When it is overkill:
• Most tasks. Seriously, do not reach for this pattern unless you genuinely need it. Two levels 
(orchestrator + workers) handle 90% of real-world use cases.
Real-world example: An automated software development pipeline. The Executive Agent decides 
what features to build based on user feedback. Manager Agent A handles frontend features, 
delegating to workers that write React components, CSS, and tests. Manager Agent B handles 
backend features, delegating to workers that write API routes, database migrations, and 
documentation.
Pattern 5: Swarm (The Bee Colony)
This is the newest and most experimental pattern. Instead of a rigid hierarchy, agents form a flexible 
network where control passes dynamically based on the situation.
How it works: Agents are loosely connected. When one agent determines it is not the best fit for the 
current subtask, it hands off to a more suitable agent. There is no central coordinator -- the agents 
self-organise.
+--------+     +--------+
| Agent  |<--->| Agent  |
|   A    |     |   B    |
+--------+     +--------+
    ^              ^
    |              |
    v              v
+--------+     +--------+
| Agent  |<--->| Agent  |
|   C    |     |   D    |
+--------+     +--------+
Key concept: Handoffs. In a swarm, agents can "hand off" the conversation to another agent when 
they recognise the task has shifted into another agent's area of expertise.
For example, a user starts asking about a billing issue (Billing Agent handles it). Mid-conversation, 
the user mentions a bug in the checkout flow (Billing Agent hands off to Engineering Agent). The 
Engineering Agent investigates and discovers the bug is in the payment integration (hands off to 
Payments Agent).

--- PDF PAGE 16 ---
When to use it:
• Customer-facing applications where conversations naturally shift topics
• Systems where you cannot predict the workflow in advance
• When you want agents to collaborate without a central bottleneck
When to avoid it:
• When you need predictable, auditable workflows
• When tasks have a clear sequential structure
• When you are just getting started (swarms are hard to debug)
Real-world example: OpenAI's Swarm framework and Anthropic's multi-agent patterns both support 
this approach. Think of a virtual assistant that can handle travel bookings, calendar management, 
email drafting, and expense reporting are each handled by a specialist, with smooth handoffs 
between them.

Key Takeaways
• Architecture is the difference between a useful agent and a frustrating one. The patterns you 
choose determine reliability, cost, and debuggability.
• Start with a single agent. Only add multi-agent complexity when the single agent approach 
genuinely fails. Premature architecture is the root of many agent nightmares.
• The five core patterns are Single Agent, Router, Orchestrator-Worker, Hierarchical, and Swarm. 
Most real-world applications use Router or Orchestrator-Worker.
• State management is non-negotiable. Whether you use in-context history, a structured object, or 
a database, you must track what has happened and what still needs to happen.
• Error handling separates toys from tools. Retries, maximum iterations, fallbacks, and human 
escalation are not optional as they are essential for any agent you want to rely on.
• Guardrails protect you from your own agent. Tool restrictions, rate limits, budget caps, and 
human-in-the-loop checkpoints prevent agents from causing damage.
• The orchestrator is the most important agent in any multi-agent system. Invest the most effort 
(and the best model) in your orchestrator's design.
• Always design for failure. Assume every tool call might fail, every agent might hallucinate, and 
every plan might need revision. The architectures that handle failure gracefully are the ones that 
work in production.

import os
def execute_tool(tool_name, tool_input):
    """Execute a tool and return the result."""
    if tool_name == "read_file":
        try:
            with open(tool_input["file_path"], "r") as f:
                return f.read()
        except FileNotFoundError:
            return f"Error: File '{tool_input['file_path']}' not found."
    elif tool_name == "list_directory":
        try:
            entries = os.listdir(tool_input["directory_path"])
            return "\n".join(entries)
        except FileNotFoundError:
            return f"Error: Directory '{tool_input['directory_path']}' not found."
    elif tool_name == "write_file":
        try:
            with open(tool_input["file_path"], "w") as f:
                f.write(tool_input["content"])
            return f"Successfully wrote to {tool_input['file_path']}"
        except Exception as e:
            return f"Error writing file: {str(e)}"
    return f"Unknown tool: {tool_name}"

Testing and Deploying AI Agents
Here is the uncomfortable truth about testing AI agents: the same input can produce different outputs 
every single time you run it. If you have ever tested a function that returns 2 + 2 = 4 and felt the warm 
glow of a passing test, prepare for a colder world. An AI agent given the same prompt might take a 
different path, use different tools, and produce a slightly different result each time.  That is by design, 
not a bug.
This is like testing a chef. Y ou can give them the same recipe and the same ingredients, but the meal 
will be slightly different each time. The question is not "did they produce the exact same dish?" but "is 
the dish good?"
That shift in thinking from deterministic testing ("did it produce the exact right answer?") to evaluation-
based testing ("is the output good enough?") is the single most important concept in this section. 
Once you internalise it, everything else falls into place.
Why Agent Testing Is Different
Let's start by understanding exactly why traditional software testing does not work for agents:
Traditional Software AI Agents
Same input always produces the same output Same input can produce different outputs each run
Y ou can assert exact values (assertEqual(result, 42)) Y ou need to evaluate quality ("is this response helpful 
and accurate?")
Bugs are reproducible Failures may not reproduce consistently
Testing is fast (milliseconds per test) Testing is slow and expensive (each test run costs 
API tokens)
Test coverage means "every code path is tested" Test coverage means "the agent handles diverse 
scenarios well"
This does not mean you cannot test agents rigorously. It means you need a different toolkit.
The Three Levels of Agent Testing
Think of agent testing as three concentric circles, from fastest/cheapest to slowest/most 
comprehensive:
Level 1: Unit Tests (Test the Pieces)
Even though the agent as a whole is non-deterministic, many of its components are perfectly 
deterministic and can be tested traditionally:
What to unit test:
• Tool functions: Does read_file("test.txt") return the file contents? Does it handle missing files 
gracefully?

--- PDF PAGE 34 ---
• Input parsing: Does the agent correctly parse a user request into structured data?
• Output formatting: Does the agent's response follow the expected schema?
• State management: Does the state object update correctly after each step?
• Error handling: Do retries work? Does the max iteration limit trigger correctly?
# Example: Unit testing an agent's tool functions
import pytest
def test_read_file_success(tmp_path):
    """Test that read_file returns file contents correctly."""
    test_file = tmp_path / "test.txt"
    test_file.write_text("Hello, world!")
    result = read_file(str(test_file))
    assert result == "Hello, world!"
def test_read_file_not_found():
    """Test that read_file handles missing files gracefully."""
    result = read_file("/nonexistent/path/file.txt")
    assert "Error" in result or "not found" in result.lower()
def test_state_updates_after_tool_call():
    """Test that agent state is updated correctly after a tool call."""
    state = AgentState(task="test task", steps=[])
    state.record_step(tool="read_file", input={"path": "test.txt"}, 
output="contents")
    assert len(state.steps) == 1
    assert state.steps[0]["tool"] == "read_file"
Unit tests are fast, cheap, and reliable. Write them for every tool function and every state 
management operation.
Level 2: Integration Tests (Test the Loop)
Integration tests verify that the agent can complete realistic tasks end-to-end. This is where you run 
the actual agent against controlled scenarios.
The key technique: Controlled test environments.
Instead of letting the agent loose on your real project, create small, self-contained test projects with 
predictable structures:

Notice that the assertion is not checking for an exact string. It is checking that the response contains 
the right information. This is the evaluation mindset at work.

Building an Evaluation Dataset
For evaluation tests to be meaningful, you need a diverse set of test cases that cover the range of 
inputs your agent will encounter in production.
How to build your evaluation dataset:
1. Start with real usage. Once your agent is running (even in beta), log the inputs it receives. 
These become your test cases.
2. Add edge cases manually. Think about the weird stuff: empty inputs, very long inputs, 
ambiguous requests, requests outside the agent's scope, requests in different languages.

--- PDF PAGE 37 ---
3. Include known-good examples. For some test cases, write the ideal response yourself. This 
gives you a ground truth to compare against.
4. Categorise by difficulty. Label each test case as easy, medium, or hard. Track pass rates by 
category to understand where your agent struggles.

Cost Management in Production
Agent costs in production can spiral if you are not careful. Here is a practical framework:
Set Budget Caps at Every Level
# Per-request budget cap
MAX_COST_PER_REQUEST = 0.50  # $0.50 maximum per user request
# Per-user daily budget cap
MAX_DAILY_COST_PER_USER = 5.00  # $5.00 per user per day
# System-wide daily budget cap
MAX_DAILY_SYSTEM_COST = 100.00  # $100 per day for the whole system
def check_budget(user_id, estimated_cost):
    """Check if this request would exceed any budget cap."""
    if estimated_cost > MAX_COST_PER_REQUEST:
        return False, "This request would exceed the per-request budget."
    user_daily_spend = get_user_daily_spend(user_id)  # From your database
    if user_daily_spend + estimated_cost > MAX_DAILY_COST_PER_USER:
        return False, "You've reached your daily usage limit."
    system_daily_spend = get_system_daily_spend()  # From your database
    if system_daily_spend + estimated_cost > MAX_DAILY_SYSTEM_COST:
        return False, "System is at capacity. Please try again later."
    return True, "OK"
The Model Cascade Strategy
Not every step needs the most expensive model. Use a cascade:

--- PDF PAGE 40 ---
Step 1: Route the request       -> GPT-4o-mini  ($0.001)
Step 2: Read and analyse files  -> Claude Haiku  ($0.005)
Step 3: Complex reasoning       -> Claude Sonnet ($0.05)
Step 4: Generate final output   -> Claude Sonnet ($0.03)
Step 5: Validate output format  -> GPT-4o-mini  ($0.001)
Total: ~$0.09 instead of ~$0.40 if everything used Sonnet
Rate Limiting
If your agent is user-facing, you need rate limiting to prevent abuse and manage costs:
Rate Limit Type Purpose Recommended Starting Point
Requests per minute per user Prevent individual abuse 10 requests/minute
Requests per minute system-wide Prevent system overload 100 requests/minute
Concurrent agent sessions Limit parallel resource usage 5 concurrent sessions per user
Max iterations per request Prevent infinite loops 20 iterations
Max tokens per request Cap per-request cost 50,000 input + 10,000 output 
tokens
# Simple rate limiting with Redis (or use in-memory for small scale)
from datetime import datetime, timedelta
# In-memory rate limiter (use Redis for production)
user_requests = {}
def rate_limit_check(user_id, max_per_minute=10):
    """Check if the user has exceeded their rate limit."""
    now = datetime.utcnow()
    window_start = now - timedelta(minutes=1)
    # Clean old entries and count recent requests
    if user_id in user_requests:
        user_requests[user_id] = [
            t for t in user_requests[user_id] if t > window_start
        ]
    else:
        user_requests[user_id] = []
    if len(user_requests[user_id]) >= max_per_minute:
        return False, "Rate limit exceeded. Please wait a moment."
    user_requests[user_id].append(now)
    return True, "OK"

Scaling Considerations
As your agent gets more users, you will need to think about scaling:

--- PDF PAGE 42 ---
Horizontal scaling (add more instances):
• Works well for stateless agents (each request is independent)
• Railway and most container platforms support this out of the box
• Make sure your state management uses a shared database, not local memory
Vertical scaling (bigger machines):
• Useful when agents need more memory for large context windows
• Less common, usually not the bottleneck
The real bottleneck is usually the LLM API:
• Most LLM providers have rate limits (requests per minute, tokens per minute)
• For Anthropic: default limits vary by plan, typically 40-4000 RPM
• For OpenAI: varies by tier, typically 60-10000 RPM
• Solution: Implement request queuing and graceful degradation. If the LLM API is rate-limited, 
queue requests and process them as capacity becomes available

Key Takeaways
• Agent testing requires an evaluation mindset, not a pass/fail mindset. The same input can 
produce different (but equally valid) outputs, so test quality rather than exact matches.
• Test at three levels: Unit tests for tools and state management (fast, cheap, deterministic). 
Integration tests for end-to-end workflows (slower, controlled environments). Evaluation tests for 
output quality (LLM-as-judge across diverse scenarios).
• LLM-as-judge is the most practical approach for evaluating agent quality at scale. Use a 
separate model to rate your agent's outputs on criteria like accuracy, helpfulness, and 
completeness.
• Build an evaluation dataset from real usage, edge cases, and known-good examples. 
Categorise by difficulty and track pass rates over time.

--- PDF PAGE 44 ---
• Monitor everything in production. Task completion rate, latency, error rate, token usage, and cost 
per task. Set alerts for anomalies.
• Cost management is a first-class concern. Use model cascades (cheap models for simple 
steps), set budget caps at every level, and cache repeated queries.
• Rate limiting protects both your wallet and your users. Limit requests per minute, concurrent 
sessions, iterations per request, and tokens per request.
• Deploy based on your needs. Serverless for simple agents, containers for complex ones, 
background workers for long-running tasks. If you are on Railway, use Bull with Redis for job 
queuing.
• Always have a fallback. When the agent fails, it should gracefully hand off to a human rather 
than producing unreliable output. An agent that knows when to ask for help is more valuable 
than one that confidently gets things wrong.
